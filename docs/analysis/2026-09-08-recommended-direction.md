## 一、我的判断：核心架构值得保留，下一步应修复“结果可信度”

这个项目不是缺少架构。它已经为真正困难的事情投入了有价值的复杂度：加密随机读、扫描失败保护、卷所有权、播放器竞态隔离。这些不是应该为了代码短一点就消除的复杂度。

相较之下，薄弱处更多发生在边界：**内部已经知道发生了什么，传到列表、搜索结果、诊断页面或发布产物时，却不再能可靠表达同一个事实。**

- 同步内部区分成功与部分失败，但持久化文案后，列表重新猜状态，可能把失败显示成成功（F02）。
- 搜索有防抖，但查询词和查询结果分别流动，可能组合出不属于同一次查询的状态（F03）。
- 已有安全日志工具，但扫描失败仍有原始异常进入可见调试日志的路径（F01）。
- 发布有标签，但手动触发与兜底取最近标签的组合，没有把构建提交和发布标签严格绑定（F11，运行可达性尚未验证）。

**所以我不推荐一轮“架构升级”。我推荐一轮小而完整的可靠性修整：事实只定义一次，跨边界不丢语义，用户不需要替系统猜测。**

成功标准不是清空所有建议，而是：同步结果可信、输入与结果一致、失败信息安全、APK 来源明确。完成这些就应该停下来重新评估，而不是惯性推进重构。

## 二、明确的推荐，而不是选项菜单

### 1. 同步结果：同一个 Room 中的类型化快照，配一次显式保留数据的迁移

**我推荐给现有关系记录增加结构化终态字段，不建历史表，不引入 DataStore 旁路。**

依据是现有数据形态：`app/src/main/java/cn/vectory/syncplayer/data/local/entity/SyncRelationEntity.kt:29-30` 已保存最近时间与结果；`app/src/main/java/cn/vectory/syncplayer/data/local/dao/SyncRelationDao.kt:44-45` 已在一次 UPDATE 中写这两者。需求是“这条关系最近一次结果”，不是审计历史系统。沿着现有聚合边界扩展，比拆到另一套存储更直接。

建议的最小设计约束：

- 领域层引入 `SyncOutcome` 表达终态、可选错误码、可选计数；存储使用稳定标识，不存枚举 ordinal，不存本地化文案作为协议。
- 终态明确区分成功、部分失败、失败、取消、未知历史；无记录单独表示。运行中的阶段不挤进“最近完成结果”。
- 仅保存当前结果展示确实需要的计数；拿不到准确值就缺省，不用 `0` 伪造确定性。不复制整份 `SyncProgress`。
- 时间、终态、错误码、计数作为一个快照原子写入。Repository 接收类型，不接收已渲染的字符串；全部生产者一起切换，不能只修列表。
- 旧文案不靠中文关键词反推：有旧记录但无法证明其状态，迁为 UNKNOWN；没有记录仍是无记录。旧文案不能成为自动展示的原始错误详情。
- 取消保留协程传播语义，不为记结果吞异常，也不许把取消当成功。若取消结果需要落库，必须先定义有界收尾和执行所有权；进程被杀不承诺留下取消记录。

这里还有一个需要主动界定的语义：`app/src/main/java/cn/vectory/syncplayer/sync/SyncPreviewViewModel.kt:129,142` 会把“预览无动作”记为最近同步结果。我建议**保留这一有用行为，但将其定义为“最近一次完成的同步检查或执行结果”**：成功扫描且确实无动作可以更新成功；有动作的预览不覆盖上次终态，扫描失败绝不能借空列表写成功。不要为了名称纯洁顺手增加“检查历史”和“执行历史”两个系统。具体展示措辞由 designer 落实。

**迁移是这项工作的组成部分，不是临发版再决定的附属步骤。** `app/src/main/java/cn/vectory/syncplayer/di/DatabaseModule.kt:27-35` 当前启用破坏性 fallback。我推荐为这次升级建立显式保留数据的迁移路径，并申请它作为现有规范的窄例外；不借机修改所有历史版本的迁移政策。

开工前需要用户批准这一实际权衡：是否接受这次定向非破坏迁移及其验证成本。我的答案是值得——为了修一个结果状态而让用户重建媒体索引和播放历史，不是合比例的代价。若不批准，整项延期，不偷偷采用破坏性升级或旁路存储。实施前须确定升级前备份/恢复办法；不把旧二进制直接打开新数据库当回滚方案。

不选择的方案：

| 方案 | 不选择的理由 |
|---|---|
| 换关键词、统一所有文案前缀 | 仍让展示字符串决定业务状态；下一次措辞调整会重现问题 |
| 在现有字符串列塞版本化 JSON | 能避免本次 schema 升级，但留下混合格式字段与隐含协议；本项目已经有 Room，不值得长期承担这层绕行 |
| 新建结果历史表 | 当前没有历史检索需求，增加保留策略和关联生命周期，超出问题大小 |
| DataStore 按 relationId 存结果 | 关系删除、ID 生命周期、跨存储写入一致性都成为新问题；不动 schema 不等于无数据风险 |

**完成边界**：所有写入点和列表消费一起闭合；部分失败不能以成功展示；未知历史不冒充成功；迁移保留原有索引与播放历史。不附赠错误处理框架重写。

### 2. 搜索：先产生稳定查询，再让这次查询拥有自己的结果

在 `app/src/main/java/cn/vectory/syncplayer/browser/SearchViewModel.kt:64-76` 收敛为一条查询主干：输入 → 300ms 防抖 → 最新查询作用域 → 结果与筛选组合。

核心不是“多加一次 debounce”，而是查询结果携带同一个被捕获的 query。新查询取消旧的结果管道；scope 切换和空查询行为保留。不要重新把两个各自防抖的分支拼回一起。

输入框可以立即显示用户正在输入的内容，结果仍有防抖延迟；这本身不是错误。必须避免的是：以 B 的查询状态解释 A 的结果，或反过来。若保留旧结果等待新结果，应能识别它所属的查询，不给用户制造已经刷新完毕的假象。

**完成边界**：快速输入、旧请求慢返回、切换范围三个序列都不出现交叉配对；不趁机重写浏览器状态架构。

### 3. 日志：修绕过点，不再造一个安全日志体系

`app/src/main/java/cn/vectory/syncplayer/sync/SyncRemoteScanner.kt:182` 改用已有 `SyncSafeLog.failure`，不把原始 Throwable 传给会向 UI 缓冲区写堆栈的日志方法。诊断需要保留安全的操作类别和错误分类，而不是为了“彻底安全”删掉所有可定位信息。

**完成边界**：该扫描错误路径不向调试页面和对应 logcat 记录传递底层 message/堆栈。这里没有证据证明远程利用，不给它贴夸大的漏洞等级。

### 4. 发布：保留手动补救，但它只能发布明确的标签

我选择 **required tag 输入 + checkout 该 tag + 提交一致性校验**，不选择删除手动发布入口。

原因很实际：个人项目需要从 CI 短暂失败中恢复；删入口把一次防错变成日后的操作负担。真正应该删掉的是“没说清楚发布谁，就猜最近的 tag”。

契约是：选择标签 → 解析 `refs/tags/$TAG^{commit}` → checkout 对应提交 → 构建与发布都绑定这份解析结果。标签命名规则复用发布脚本规范；非法或缺失 tag 立即拒绝。校验标签解引用后的 commit，不比较 annotated tag object。正确的手动请求不应仅因最初从某个分支发起就被拒绝。

文件范围沿用原路线 T4：`.gitea/workflows/release.yml`、`scripts/ci/release-check.sh`、`scripts/gitea/publish-release.sh`。同时对齐 T11 的产物文档：APK + SHA256SUMS，不恢复已被有意移除的 mapping 上传。

**完成边界**：缺失/错误标签拒绝；正常标签与手动补发得到一致的提交绑定；后续用隔离 fixture 验证，不用生产 release 做试验。不扩大为 CI 平台改造。

## 三、执行顺序：三次有明确终点的交付

这里使用批次 A/B/C 表示先后，不沿用原路线中容易与严重性混淆的阶段名 P0/P1。**批次不代表安全等级，也不是强行串行所有任务。**

| 交付 | 范围 | 为什么这样排 | 退出条件 |
|---|---|---|---|
| **A：先堵住低成本的不可信边界** | 日志 F01、搜索 F03、发布 F11 + 同域文档 F10；同步结果迁移决策并行完成 | 改动局部且收益明确；迁移决策不能被琐碎整理挤到最后 | 日志安全摘要、查询一致性、标签绑定各自闭合；迁移方向批准或明确延期 |
| **B：把结果协议做完整** | F02：类型、迁移、所有写入点、列表展示 | 最重要的跨层修复需要完整交付，不能只完成底层留 UI 猜字符串 | 新旧数据语义清楚，失败可区分，保留数据升级路径成立 |
| **C：设置页消除具体摩擦，然后停下** | F04/F05/F06：组合期移除阻塞查询、删除无消费者的空间状态、权限失败给出可操作反馈 | 解决真实的体验与资源使用问题，而非追求层次漂亮 | 无组合期 Provider 查询、无无用空间刷新、授权失败不静默且不回显 URI |

设置页与结果协议没有技术依赖；若 B 等待批准，C 可先行。发布也不与 schema 升级捆绑。若有独立资源可提前推进，但不要因可并行就打开所有任务。逻辑 writer 最多两个，UI 设计交给 designer，双方不并行写同一文件。父协调者负责协议整合与证据核对；未来实施的验证负责人负责运行证据。本轮不执行这些验证。

设置页的取舍也应明确：**删除未消费的 `usableSpaceLabel` 链路，而不是替它建设调度框架。** 目录名按 URI 变化异步读取，失败回退固定资源文案；不使用可能返回完整 URI 的 `fallbackUriLabel`。授权失败反馈只解决“失败了、没有切换、如何重试”，不重设计整个设置页。

## 五、验证投入：关注会失去什么，而不是测试数量

以下是**未来实施后的验证设计**，不是本轮测试结果，也不是现在要运行的命令。

| 风险边界 | 最有价值的证据 | 不接受的替代品 |
|---|---|---|
| 结果终态 | 成功/部分失败/失败/取消/无记录/未知历史的类型与展示映射；全写入点覆盖 | 仅断言某句中文是否包含“失败” |
| 迁移 | 用旧 schema 构造关系、媒体索引、播放历史，升级后逐项保留；核对旧结果转 UNKNOWN | 空库建表成功、编译通过就宣称迁移安全 |
| 查询一致性 | 可控时间与延迟，证明旧查询不能污染新查询，scope/空查询行为保留 | 仅搜索一次看到正确结果 |
| 发布绑定 | 隔离仓库中验证 annotated tag、错误 tag、checkout 不一致和正常手动补发 | 真的发一次生产 release 看看 |
| 设置页 | 可替换 I/O 状态源；权限失败事件不含 URI/message；旧请求不能覆盖新 URI 状态 | 只静态搜索 Screen 没有直接 query 就断言不卡顿 |
| Provider/Service | 先写可复现的 FD 关闭、卷切换、前台服务生命周期序列，再决定设备验证投入 | 用单测数量推断系统集成已经可靠 |

Provider/Service 的序列设计不必等待所有低优先级整理结束。它可以作为独立的小型验证准备，但不应扩展成“先建完整设备 CI 才能继续修复”。

未来代码变更仍须执行项目要求的 `compileDebugKotlin` 及针对性测试；静态检视和 LSP 不能替代它。当前仅静态分析，无法承诺帧耗时、设备兼容性、真实服务生命周期或 CI 在线行为。

## 六、停止条件与后续决策

当 A/B/C 达到退出条件，我建议先交付并使用，而不是继续按原版 T1–T13 全部扫尾。下一轮只由实际使用问题和明确失败序列驱动。

需要用户决定的不是十几个实现细节，而是两个边界：

1. 是否批准这一轮可靠性修整进入实施。
2. 是否批准同步结果升级采用一次定向、保留数据的 Room 迁移例外。

其余选择已经给出推荐：保留手动 tag 发布、同关系记录存结构化结果、删除无用状态、不建旁路存储、不改播放器架构。若实施时出现与这些假设冲突的新证据，再调整；不是预先把每一个小决定都退回给用户。

**我希望这轮改动后的项目不是“架构更多”，而是更少让人怀疑：看到的同步状态可信，搜索结果属于当前查询，失败不会泄漏信息，安装包对应明确的源码。**
