## 1. 背景

2026-08-23 的深度代码质量审计（Run ID `20260823-1758_deep-code-quality`）在 v12.1.0 基线上确认了 1 个 P2 正确性缺陷（CQ-001）及多项可维护性观察。基线本身健康：`compileDebugKotlin`、`testDebugUnitTest`（31 套件 / 352 测试全过）、`lintDebug`（0 error，91 warning + 1 hint）均通过。

**CQ-001（已验证）**: SMB/SFTP 阻塞操作在协程已取消后完成的普通异常（超时/IOException）会在 transport 边界被包装成 `SyncException`，绕过调用方的 `catch (CancellationException)` 守卫，导致用户取消的操作被误报为 FAILED/error：

- `app/src/main/java/cn/vectory/syncplayer/sync/sftp/SftpFileClient.kt:60-85`（connect）及 `:121/:187/:242`（list/download/delete）
- `app/src/main/java/cn/vectory/syncplayer/sync/smb/SmbFileClient.kt:63-97`（connect）及 `:138/:167/:263/:327`
- 受影响调用方：`SyncEngine.kt:256-378`（dryRunLocked）、`:819-858`（dryRunDelete）、`:863-1013`（executeDeleteLocked）、`:449-675`（下载管线失败计费）
- 根因：取消策略依赖 `catch (CE)`，而 CE-first 只在抛出对象本身是 CE 时有效；非协作阻塞操作可在 job 取消后产生普通异常，transport 翻译前未检查 job 状态。

**结构观察（6.2/6.4）**: `VideoItemDao.updateStarByPath` 的 path-based fallback 当前不可达但属危险潜伏 API（跨 relation 写入）；`SyncEngine`（1060 行）与 `BrowserViewModel`（640 行）是高变更复杂度热点。

**工具链现状**: 编译器仅余测试 stub 参数名告警（`app/src/test/java/cn/vectory/syncplayer/storage/volume/EncryptedMediaStoreTest.kt:239-245`，`relPath`/`dirRelPath`）；lint 91 warning 中项目源码可修部分尚未清零。

用户已批准：采纳方案 B（分阶段单版本整改），版本号 12.2.0。

## 2. 目标 / 非目标

### 目标

1. **G1 取消正确性**: 修复 CQ-001——SMB/SFTP transport 异常翻译边界全面 CE-first + `ensureActive()`，取消始终以 `CancellationException` 可观察。
2. **G2 删除 dead API**: 移除 `VideoItemDao.updateStarByPath` 到 UI 的完整 dead fallback 链及对应测试分支。
3. **G3 SyncEngine 拆分**: 按生命周期拆为 4 个协作类，Engine 只保留互斥、阶段顺序、公开 API。
4. **G4 BrowserViewModel 拆分**: 新增 `BrowserContentCoordinator` 承接 Flow 组合逻辑。
5. **G5 工具链清零**: 修项目源码内的 compiler 告警与 lint warning（仅限不改行为的项 + 逐项确认的 unused resources）。

### 非目标

- **不改安全契约**: AEAD v2 格式、E8 扫描失败守卫、卷所有权 fail-closed、重试瞬态码白名单、对外 UI API（公开 StateFlow/方法签名保持不变）。
- **不动依赖/构建**: 不升级任何依赖、Gradle、AGP、targetSdk/compileSdk。
- **不处理第三方二进制告警**: `Aligned16KB`（io.mockk）、`TrustAllX509TrustManager`（无法映射到项目源码）、`NewerVersionAvailable`/`GradleDependency`/`AndroidGradlePluginVersion`/`OldTargetApi`/`MonochromeLauncherIcon` 等依赖升级类建议全部跳过。
- 不做 UI 视觉/交互变更，不做 `androidTest`/真机验证计划之外的扩展。

## 3. 方案比较

| 方案 | 内容 | 优势 | 代价/风险 | 结论 |
|---|---|---|---|---|
| **A 单次大重构** | 一个分支内同时完成 G1–G5 | 一次合并；上下文集中 | diff 巨大难 review；正确性修复（CQ-001）与结构重构耦合，回滚粒度差；与安全红线距离过近 | 否决 |
| **B 分阶段单版本**（选中） | 5 个有序 Phase，独立提交、独立验证，共同构成 12.2.0 | 正确性修复最先合入且不被重构污染；每阶段可单独回滚；验证矩阵分层清晰 | 总耗时略长（每 Phase 各跑门禁）；需要严格的写域划分防冲突 | **采纳** |
| **C 仅正确性延期重构** | 只修 CQ-001 + 回归测试，G3/G4/G5 延后 | 最小 diff、最快发版 | 复杂度热点继续增长；dead API 继续潜伏；lint 债务不清零，下轮审计重复出现 | 否决 |

方案 B 的决定性理由：CQ-001 修复必须先于 SyncEngine 重构落地（Phase 1 → Phase 3 顺序），使取消语义在重构前已被测试固化，重构 merely 保持绿灯而非同时引入语义。

## 4. 阶段设计

### Phase 1 — TDD 固化取消行为（sync transport）

先写失败测试再修实现。覆盖 **12 个语义边界**：11 个异常翻译/降级 catch（CE-first + 转换前 `currentCoroutineContext().ensureActive()`）和 1 个递归遍历活性检查：

| # | 文件 | 方法 |
|---|---|---|
| 1–5 | `SftpFileClient.kt` | `connect()`(:60)、`deleteFile()`(:242)、`downloadTo()`(:187)、`listDirectories()`(:121) 的 4 个异常边界；`listFilesRecursive()`(:147) 阻塞遍历前检查 |
| 6–12 | `SmbFileClient.kt` | `connect()`(:63)、`deleteFile()`(:327)、`downloadTo()`(:263)；`listShares()`(:138) 的外层列表和逐条属性读取；`listDirectories()`(:167) 的外层列表和逐条属性读取，共 7 个异常边界 |

统一模式：

```kotlin
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    currentCoroutineContext().ensureActive()
    throw SyncException(..., cause = e)
}
```

要点：

- **测试先行**: 按 CQ-001 Recommended Regression Test 构造可注入的假阻塞操作——信号量通知"阻塞已开始"、忽略取消、测试中取消 parent、随后抛 `IOException("simulated transport timeout")`。包装型边界断言以 CE 终结而非 `SyncException`/FAILED/failed-action 计费；逐条降级边界断言取消后不继续处理后续条目。外层“返回空列表”边界在修复前可能已由 `withContext` 的正常完成检查恢复 CE，因此列为 pre/post 守卫测试而非强制红灯。覆盖 `connect()→dryRun`、`connect()→executeDelete`、per-file download/delete 与逐条遍历副作用。
- **阻塞遍历检查**: SFTP 的 `listFilesRecursive()` 在 `sftp.ls(currentPath)` 前检查 active；SMB 的 `listDirectories()` 在外层 `listFiles()` 失败和逐条属性读取降级前分别检查 active。这样取消不会被“返回空列表”或“跳过单条目”吞掉。
- **保留 IOException 目录浏览降级**: `listShares()` 现有"catch Exception → log + 返回空列表"及 `listDirectories()` 的逐条降级语义在**未取消**时保持不变——`ensureActive()` 只在 job 已取消时改写结果为 CE，普通 IOException 仍走原降级路径。为该语义补一条守卫测试。
- **NonCancellable 仅限必要清理**: 当前两个 `testConnection()` 已在 catch 中执行非挂起/容错 `disconnect()` 后原样重抛，因此不需要修改；若实现期间出现必须挂起的取消清理，只允许用 `withContext(NonCancellable)` 窄域包裹清理，禁止宽域使用。
- **消除附带的取消恢复依赖**（审计 6.3）: `downloadTo()` 显式传播 CE，不再依赖 `store.cancel()` 进入另一 `withContext(IO)` 偶然恢复。

### Phase 3 — SyncEngine 拆分（sync engine lane）

现状：`SyncEngine.kt` 1060 行，混合扫描/下载/删除/待办任务四类生命周期职责 + 互斥编排。

拆分后（新文件均置于 `app/src/main/java/cn/vectory/syncplayer/sync/`）：

| 新类 | 承接职责（自现有方法迁移） | 依赖注入 |
|---|---|---|
| `SyncPendingTaskManager` | `setPendingTask`(:129)、`consumePendingTask`(:191) | `PendingSyncActionDao` |
| `SyncDeleteExecutor` | **DELETE_BOTH 路径**：`executeDeleteLocked`(:863) 删除执行体、`deleteStoreMedia`(:1020)、`deleteStoreThumb`(:1042)、卷所有权校验、index-only delete 语义 | `EncryptedMediaStore`(Lazy)、`VideoRepository`、`SyncLogRepository` |
| `SyncRemoteScanner` | `dryRunLocked`(:256) 的远端扫描/对比/`SyncAction` 推导、E8 守卫（`RemoteScanIncompleteException` 清空 toDownload/toDelete） | `RemoteFileClientFactory`、`VideoRepository`、`SyncRelationRepository` |
| `SyncDownloadPipeline` | **`executeSync`(:381) 下载主管线 + DELETE_LOCAL 尾段**：下载循环、`extractMetadata`(:121)、`SyncSpaceChecker` 预检、失败计费与重试白名单判断（`isRetryableSyncException` :249）、DELETING 阶段 progress 与终态汇总（`wrapSyncException` :239 随扫描归 SyncRemoteScanner） | `VideoRepository`、两个 MetadataExtractor、`StoragePaths`、`EncryptedMediaStore`(Lazy)、`SyncDeleteExecutor`（复用 `deleteStoreMedia/Thumb`） |

**Engine 仅保留**: `progressPublisher` 单实例（传引用给各协作类，进度仍单点汇总）、`storageOperationMutex` + relation mutex（`syncMutexMap`）互斥编排、pending-task 的 mark/finalize/NonCancellable 取消清理编排、阶段顺序（扫描→下载、删除）、公开 API 不变——`dryRun`/`executeSync`/`dryRunDelete`/`executeDelete`/`setPendingTask`/`consumePendingTask`/`progress`/`resetProgress`/`isSyncRunning` 签名与语义完全保持。调用链固定为：`consumeAndExecute → Engine.executeSyncLocked`（仅持 relation mutex 的壳）`→ pipeline.executeSyncLocked`。DELETE_LOCAL（同步流程尾段）归 SyncDownloadPipeline；DELETE_BOTH（独立删除入口）归 SyncDeleteExecutor——两者共享卷所有权 fail-closed 语义。

**迁移顺序（每步独立提交，全绿后进下一步）**: Pending → Delete → Scanner → Download。理由：PendingTask 最独立；Delete 有明确的失败边界测试；Scanner 依赖 E8 语义（先固化）；Download 最复杂且依赖前三者的稳定接口。

**安全 invariants 迁移时逐条保持**（迁移后在类 KDoc 中显式标注归属）：

1. E8：部分远端快照绝不推导 DELETE_LOCAL（归 SyncRemoteScanner）。
2. 卷所有权 fail-closed：volumeId 不匹配计 FAILED；index-only delete 返回成功（归 SyncDeleteExecutor）。
3. CE 先传播，重试仅瞬态码白名单（归 SyncDownloadPipeline / 各类 catch）。
4. `CancellationException` 不被 `catch (Exception)` 吞——全部新类沿用 CE-first。

## 7. 回滚与风险

**回滚策略**: 每 Phase 独立小提交（transport 修复、每类拆分、每批 lint 各自成型），任一阶段验证失败仅 revert 该阶段提交；公开 API 全程保持，使回滚不产生调用方破损。Phase 3 内部四步迁移各自可独立回滚。

| 风险 | 等级 | 缓解 |
|---|---|---|
| 取消修复引入误吞异常（把真实失败当取消） | 高 | `ensureActive()` 语义仅在 job 已取消时抛 CE；专项测试同时覆盖"未取消时普通异常仍翻译为 SyncException"反向用例 |
| SyncEngine 拆分丢失互斥语义（并发 sync/delete 竞态） | 高 | 互斥体全部留在 Engine，新类不持锁；4 组集成测试零修改作为回归闸门 |
| E8/卷所有权迁移中语义漂移 | 高 | invariants 清单逐条迁移标注；`SyncEngineBoundaryTest`（E8/边界）+ 新类单测双覆盖 |
| BrowserViewModel 拆分引入重组风暴/状态丢失 | 中 | 公开 StateFlow 名称/类型零变化；行为测试 + 手动 smoke（浏览/排序/搜索/刷新/星标） |
| Coordinator 与 ViewModel 双向依赖 | 中 | 接口纪律：只读流 + 意图方法，lint 级 code review 检查 |
| 删除"unused"资源实为动态引用 | 中 | 逐项 grep 确认后才删；存疑保留并记录 |
| `UsableSpace`/`ApplySharedPref`/`Recycle` 行为差异 | 低 | 三者均为 suppression + 书面理由（凭证同步落盘一致性 / 流所有权移交 / 卷 UUID 映射不可行），不改运行时行为；理由随代码注释与 review 记录留痕 |
| downloadTo 显式 CE 后清理路径不执行 | 中 | `NonCancellable` 窄域清理 + 既有清理测试保持全绿 |
