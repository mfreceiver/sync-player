## Candidate Findings

### F1. Gesture-seek: displayed target/preview diverges from actual seek landing point while playing — CONFIRMED (P3)
- Mechanism: GesturePlayerView freezes the seek base (`seekBasePositionMs = currentPosition` at gesture start, GesturePlayerView.kt:101-104); PlayerScreen's 200ms polling loop stops updating `gestureView.currentPosition` during the gesture (PlayerScreen.kt:244-246, guard added in commit d150590). Overlay text and seek-preview frame are computed from the frozen base (`targetMs = seekBasePositionMs + seekOffsetMs`, GesturePlayerView.kt:111-113; preview uses `uiState.gestureSeekPosition` from that same target, PlayerScreen.kt:382-384/432-435).
- But the actual seek on ACTION_UP uses the LIVE player position: `newPos = (exoPlayer.currentPosition + offsetMs)` (PlayerScreen.kt:309-312) and `viewModel.onGestureSeekFinished` uses `_currentPosition.value + offsetMs` (PlayerViewModel.kt:341-346), both of which keep advancing every 200ms while the video keeps playing during the gesture.
- State owner: GesturePlayerView (frozen base) vs ExoPlayer live position. Trigger: horizontal drag seek on a playing video. Expected: playback lands at the position shown in the seek pill/preview. Actual: lands ahead by ~gesture duration (at 1x) + up to 200ms. Paused playback is consistent; only playing playback diverges.
- Evidence: PlayerScreen.kt:309-313, 244-246; GesturePlayerView.kt:101-113, 174-190; PlayerViewModel.kt:341-347. Runtime-or-static: static logic proof (no device). Framework guard: none. Counterargument: some players intentionally apply offsets to the live position — but then the overlay and preview frame should be live-based too; the display is inconsistent with the action either way. Git: base-freeze introduced in d150590 (2026-04-21) which fixed thumbnail drift but did not reconcile the final seek target.

### F2. Player seek bar has no semantics — invisible and inoperable to TalkBack — CONFIRMED (P3, a11y)
- Element: custom seek bar = plain `Box` with raw `pointerInput` drag handler + fill-width fraction Box (PlayerScreen.kt:874-916).
- Mechanism: `pointerInput` without `Modifier.semantics {}` produces no clickable/slider/toggle node; the bar is not focusable and not announced by TalkBack; no `progressBarRangeInfo`, no `stateDescription`. A screen-reader user cannot determine position, duration (the adjacent time Text is read but the bar itself is not operable), nor seek by accessibility actions. Same for `MinimizedProgressBar` (PlayerScreen.kt:929-948, no range info) — secondary.
- Evidence: PlayerScreen.kt:874-916. Statically verifiable: zero `semantics` import in PlayerScreen.kt. strings.xml has usable labels (player_pause etc., lines 313-318) but no slider semantics wired. Counterargument: personal-use app, player UIs are frequently gesture-driven; still a provable a11y gap for the primary transport control. Runtime-or-static: static.

### F3. Player settings popup: direction chips unlabeled, no selected state; speed chips no selected state — CONFIRMED (P3, a11y)
- Element: `IconOptionChip` local to PlayerScreen (PlayerScreen.kt:1031-1048): 40dp `Surface(onClick)` whose only child is `Icon(contentDescription = null)` (ScreenRotation / Fullscreen, PlayerScreen.kt:983-1006). TalkBack announces an unlabeled button; `selected` state is purely visual (background alpha). `TextOptionChip` ("1x/1.5x/2x", PlayerScreen.kt:1050-1075) announces the label but not selection (`Role.RadioButton`/`selected` semantics absent).
- Contrast: the browser's equivalent `IconOptionChip` in BrowserSortFilter.kt:306-326 does set `Modifier.semantics { contentDescription = ... }` — the pattern exists in-repo and was not applied here. Touch target 40dp (<48dp) and 32dp respectively.
- Evidence: PlayerScreen.kt:983-1006, 1031-1075 vs BrowserSortFilter.kt:306-326. Runtime-or-static: static. Counterargument: transient popup in a fullscreen player; low usage frequency.

### F4. Advanced filter dialog: star-filter-mode toggle is an unlabeled 36dp button; star input targets 28dp and value-less descriptions — CONFIRMED (P3, a11y)
- Element: BrowserScreen.kt:480-499 — `Surface(onClick, Modifier.size(36.dp))` whose content is either Text("="/" >"/"<") (read as bare operator) or `Icon(modeIcon, contentDescription = null)` when OFF (BrowserScreen.kt:496) → an icon-only unlabeled button in the OFF state; no `contentDescription`/`stateDescription` explaining it cycles EQ/GT/LT/OFF.
- `StarRatingInput` (StarRatingInput.kt:32-52): each star `clickable` without role/label; `contentDescription` is `star_rated`("已评分")/`star_unrated`("未评分") (strings.xml:326-327) — does not convey which star (1..5) is tapped; touch target 28dp (AdvancedFilter uses starSize=28.dp, BrowserScreen.kt:501-506) < 48dp.
- Trigger: TalkBack user opens 高级筛选. Expected: mode button announces its function + state; stars announce value. Actual: silence/bare symbol. Runtime-or-static: static. Counterargument: dialog also has visible text label (browser_star_rating) nearby, but the controls themselves are unannounced.

### F5. Consecutive identical errors are dropped (LaunchedEffect keyed on error value) — PLAUSIBLE (P3)
- Pattern: `error?.let { LaunchedEffect(it) { snackbarHostState.showSnackbar(it); viewModel.clearError() } }` in BrowserScreen.kt:345-350, SearchScreen.kt:305-310, PlayerScreen.kt:504-509 (playerError).
- Mechanism: while the first snackbar is suspended in `showSnackbar` (~4s Short duration), a second error with the SAME string leaves the key unchanged → effect not restarted → second error is never shown; the first effect's `clearError()` then clears the newer error. Errors that differ by string restart the effect (acceptable replace).
- Trigger: two identical failures within the snackbar window (e.g., rapidly toggling trash twice and both toggles fail with same code → same mapped string). Evidence standard: mechanism is static-provable; realistic occurrence frequency is low. Counterargument: errors are rare and mostly user-paced >4s apart; StateFlow distinct-until-changed also collapses identical values even outside the window. Verdict: PLAUSIBLE, low.

### F6. ImageViewer: zoom/pan transform not reset when switching images — PLAUSIBLE (P3)
- `ZoomableImage` holds `scale/offsetX/offsetY` in plain `remember` keyed to nothing (ImageViewerScreen.kt:247-250); `entity` (current image) changes on swipe but transform state persists. Swiping IS permitted while zoomed at the pan edge (`canSwipeHorizontal`, ImageViewerScreen.kt:317-331), so the next image loads pre-zoomed/panned with no reset (`loadImage` does not touch these; no `LaunchedEffect(entity)` reset). Double-tap resets (343-348) — the only recovery.
- Trigger: zoom into image A, pan to edge, edge-swipe to image B → B appears zoomed. Expected: each new image starts at scale 1 (ContentScale.Fit). Static: yes. Counterargument: none found; likely just missing reset. Verdict: CONFIRMED as logic gap, impact low (recoverable via double-tap) → reported P3.

### F7. Playback position saved only on player dispose; ON_STOP does not persist — PLAUSIBLE (P3)
- `saveProgress` is called only from DisposableEffect.onDispose, on switch-to-next/prev, and STATE_ENDED (PlayerScreen.kt:138, 192, 342, 354). The lifecycle observer ON_STOP only pauses (PlayerScreen.kt:254-267). If the process is killed while the app is backgrounded mid-video (composition alive, no dispose), progress since the last save is lost; resume restarts from the previous session's position.
- Trigger: play → background → LMK/process death → relaunch. Static: call-site proof. Counterargument: Media3 position is also in-memory; persistence-on-exit is a deliberate pattern for this app; impact limited to position accuracy. Verdict: PLAUSIBLE.

### F8. App-lock biometric cooldown can be reset via configuration change — PLAUSIBLE (P3, security-adjacent UI state)
- LockScreenOverlay keeps `failCount/isCooldown/cooldownRemaining` in plain `remember` (LockScreenOverlay.kt:28-31) inside the composition. A uiMode change (system dark-mode toggle from quick settings) recreates the activity (uiMode NOT in manifest configChanges) → overlay state resets → `LaunchedEffect(Unit)` (LockScreenOverlay.kt:59-65) immediately re-prompts biometrics with cooldown cleared.
- Expected: anti-bruteforce cooldown (5 failures → 30s) should survive recreation (VM / SavedStateHandle / AppLockManager). Actual: toggling dark mode during cooldown re-arms the prompt. Static: recreation + state-loss provable; actual bypass requires the attacker to reach quick settings (possible while locked on API 34+ unless FLAG_SECURE blocks screenshot only — it does not block quick settings). Counterargument: biometric rate-limiting is also enforced by the framework (BiometricPrompt has its own throttling), so app-level cooldown bypass is defense-in-depth loss only. Verdict: PLAUSIBLE.

### F9. GesturePlayerView does not request system-gesture exclusion at screen edges — PLAUSIBLE (P3, interop)
- GesturePlayerView.kt:163-198 handles all touches itself but never calls `setSystemGestureExclusionRects`. On gesture navigation, horizontal seek drags that begin in the left/right edge zones and vertical brightness/volume drags from top/bottom edges will be intercepted by the system (back/home) instead of the app. Fullscreen content maximizes edge overlap.
- Static: absence provable; user impact depends on device navigation mode + OEM exclusion limits (`systemGestureExclusionLimitations` — Android caps exclusions to 200dp per edge, and back-gesture exclusion is allowed but limited). Verdict: PLAUSIBLE (impact device-dependent).

## Rejected Hypotheses

- **R1: seek-preview frame extraction blocks the main thread.** `SeekPreviewExtractor.extractFrameAtPosition` is `suspend` with `withContext(Dispatchers.IO)` (SeekPreviewExtractor.kt:144-145); `beginSession/endSession` also off-main (67-112). `getCachedFrame` is an LruCache lookup only. REJECTED.
- **R2: `LaunchedEffect(uiState.isPlaying)` polling loop has stale `uiState` closure (would break the gesture-seek guard / seekTarget clearing).** `uiState` is a `by collectAsStateWithLifecycle()` delegate — every read inside the loop reads `State.value` fresh. Guard works as designed. REJECTED.
- **R3: `FileContextMenuDialog` `localStar` remembered without item key shows previous item's rating.** The dialog is gated by `showContextMenu != null` (BrowserScreen.kt:257); dismiss sets null → composition exits → `remember` re-initialized per open. Same gating protects `DirectoryTreeDialog` `selectedPath`/`childrenMap` and `FolderContextMenuDialog` stats. REJECTED (fragile pattern, but no reachable defect).
- **R4: Lazy lists missing keys → item-state mixups on sort/filter.** Keys present in all lists: browser grid/staggered/list `key = { it.relativePath }` (BrowserContent.kt:195, 303, 381), search `key = { it.relativePath }` (SearchScreen.kt:236), sync preview prefixed keys `dl_`/`rm_` (SyncPreviewScreen.kt:379-388), directory tree keyed by fullPath (DirectoryTreeDialog.kt:144). Note: `contentType` is not set anywhere (directory vs file items alternate) — composition-recycling inefficiency only, no correctness issue. REJECTED as a finding (contentType noted as minor).
- **R5: dialog visibility / sort / filter should use rememberSaveable for rotation.** Orientation/screenSize are self-handled via manifest configChanges (no recreation). Remaining recreations (uiMode/fontScale) dismissing dialogs matches platform behavior; sort/filter/viewMode/gridColumns/browseMode live in ViewModel + DataStore persistence (BrowserContentCoordinator init + setters), surviving recreation and process death. Dialog visibility loss alone is not user-harmful. REJECTED as a finding.
- **R6: seek-preview LaunchedEffect(isSeekingActive) captures stale uiState.** Same delegate-fresh-read pattern as R2. REJECTED.
- **R7: heavy work during recomposition (filter/sort on main thread).** BrowseItemBuilder runs inside coordinator `mapLatest` under injected `ioDispatcher` (BrowserContentCoordinator.kt:193-239), debounced 300ms for filter inputs; folder switches intentionally un-debounced with cancellation via flatMapLatest/mapLatest. REJECTED (well-engineered).
- **R8: playerListener/gestureListener rebuilt per recomposition or reading stale uiState.** Listener objects built once in `remember`; `uiStateRef = rememberUpdatedState(uiState)` used for callback-time reads (PlayerScreen.kt:180-222, 291-392). `isExiting`/`initialVolume` delegate writes are fresh. REJECTED (explicitly well done).
- **R9: ExoPlayer created with `remember` leaks or restarts on config change.** DisposableEffect(Unit) releases player + nulls surface player + restores brightness/insets/orientation on dispose (PlayerScreen.kt:116-143); AndroidView factory pattern is one-view-per-composition; ON_STOP pauses. REJECTED.
- **R10: `LaunchedEffect(uiState.videoItem)` restarts playback mid-session (setMediaItem+prepare on unrelated uiState change).** `videoItem` only mutated in `loadVideo`; record refreshes write `playbackRecord`. REJECTED.
- **R11: high-frequency gesture-seek positions in `PlayerUiState` violate State Splitting (architecture.md).** `userSeekPosition`/`gestureSeekPosition` update per motion frame inside the main `_uiState` → whole PlayerScreen recomposes per drag frame. Static convention deviation is real, but no provable expensive work (tree is shallow, AndroidView skips, preview throttled to 50ms poll + cached extraction); 200ms playback position IS properly split (currentPosition StateFlow + narrow subscribers SeekProgressBarWithTime/MinimizedProgressBar, PlayerScreen.kt:859-948, consistent with the spec). Not promoted per evidence standards. REJECTED as a finding; recorded as convention observation.
- **R12: LockScreenOverlay misbehaves on config change generally.** `isLocked` is app-scoped (AppLockManager), overlay re-composes and re-prompts; only cooldown state is lossy (F8). REJECTED except as F8.
- **R13: hardcoded user-facing strings bypassing strings.xml.** Only hardcoded Texts are " · " separators, "SMB"/"SFTP" protocol labels, and "1x/1.5x/2x" speed labels (acceptable tokens); all real copy uses stringResource. REJECTED (i18n convention held).
- **R14: i18n/formatFileSize units hardcoded.** "B/KB/MB/GB" units universal; Locale-aware number formatting used. REJECTED.
