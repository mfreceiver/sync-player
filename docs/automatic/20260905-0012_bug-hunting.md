### BUG-001 部分完成的 DELETE_BOTH 在下次同步"复活"已删除文件

- **Severity**: High（用户删除意图静默丢失 + 带宽/配额浪费循环）
- **Confidence**: High（两阶段实验确定性复现）
- **Source Location**:
  - `app/src/main/java/cn/vectory/syncplayer/sync/SyncDeleteExecutor.kt:88-136`（本地先删：`playbackRepository.deleteByVideoId` + `videoRepository.deleteByRelativePathAndRelationId` 在远端删除**之前**）
  - `app/src/main/java/cn/vectory/syncplayer/sync/SyncRemoteScanner.kt:97-104`（dryRun 纯以 `localMap[localRelPath] == null → DOWNLOAD` 推导，不查 pending 删除队列）
- **Missing Test Scenario**: sync 模块 + 序列「DELETE_BOTH 本地成功/远端失败 → 下次 dryRun」+ failure mode「远端删除抛异常」。
- **Trigger**: 用户在回收站预览确认删除；本地密文+DB 行删除成功后，远端 `client.deleteFile` 抛异常（网络闪断、连接重置、权限抖动）。之后任何一次普通同步（mirror 模式）。
- **Execution Path**: `executeDeleteLocked`（本地删除成功 → remote 异常 → `failedActions++`，行已删）→ 用户稍后 `dryRunLocked`（远端有文件 + 本地无行 → DOWNLOAD）→ 重新下载为**全新未删除条目**；远端删除若持续失败，循环往复。
- **Minimal Reproduction**: `app/src/test/java/cn/vectory/syncplayer/bughunt/BH_TrashResurrectionTest.kt`（两阶段：phase1 真实 executor + 抛异常的远端删除，coVerify 行已删；phase2 真实 scanner，断言 toDownload 重新包含该路径）。
- **Commands Executed**: `./gradlew testDebugUnitTest --tests "cn.vectory.syncplayer.bughunt.BH_TrashResurrectionTest"` → BUILD SUCCESSFUL（断言全部成立）。
- **Expected**: 挂起的 DELETE_BOTH 意图应阻止 dryRun 为同一路径推导 DOWNLOAD；或 executor 在远端 ack 前不删本地行。
- **Actual**: `dry.toDownload == [trashed.mp4]` —— 回收站文件作为新条目复活。
- **Repeatability**: Deterministic（门控/stub，无时序依赖）。
- **Root Cause**: 删除动作被拆成两个不可回滚的半步且无持久化意图记录；扫描推导只看当前快照差集。
- **Impact**: 数据不丢失（方向是"多下载"），但删除意图丢失；移动网络下反复浪费流量；用户看到"删了又回来"。
- **Relevant Git Context**: 删除管线由 `b115aa8`（SyncEngine overhaul）引入、`bc9ac4b` 加固；当时未考虑远端失败后的重推导。
- **Recommended Regression Test**: sync 模块 + 「DELETE_BOTH 远端失败 → dryRunLocked」序列，断言 toDownload 不含该路径（修复方向 A）或 executor 失败时本地行保留（修复方向 B）。
- **Recommended Fix Direction**: A) dryRun 排除仍在 pending DELETE 队列中的路径（查 PendingSyncActionDao）；或 B) DELETE_BOTH 改为 remote-first / 本地行延迟到远端 ack 后再删（本地先删密文但保留行 + tombstone）。B 语义更干净但改动大；A 是最小补丁。
- **Independent Reproduction**: 待第二轮独立复现（见 Repeatability 注：同实验由主 Agent 亲自运行两轮，结果一致）。

### BUG-010 SFTP deleteFile 非幂等 —— 远端文件已消失时报 REMOTE_DELETE_FAILED

## Interesting Tests That Passed

1. **存储写/删/改与 DB 操作的全局 `storageOperationMutex` 串行化**（1f2205d）—— dual-mutex（全局 + 每 relation）+ `consumeAndExecute` 的原子消费使「双 sync 并发」「reset 与 sync 交错」在结构上不可达；唯一例外 `dryRunDelete` 只读不改数据（见 REJECTED-4）。
2. **E8 部分快照防护**：SFTP/SMB 递归扫描逐目录抛异常、dryRun catch 无条件清空 toDownload/toDelete、仅 try 完整路径可返回非空 —— 四条部分列表来源全部关闭；`listDirectories` 的空列表退化只服务浏览 UI，不进 dryRun。
3. **取消后恢复不会写坏半截文件**：cancel 只删 tmp；openWrite 截断（FileVolume）/先删后建（SafVolume）；AEAD 每次尝试写新 header/IV。遗留 tmp 不会被 purge 误当 legacy（严格 ASCII 校验）。
4. **旧密文不会被 cancel 误删**：`store.cancel` 只删 `.enc.tmp`；`<id>.enc` 仅被成功的 finalize rename 替换（BUG-007 证明的是 finalize **之后**的清理缺口，不是 cancel 破坏旧密文）。
5. **双取消幂等**：`SyncService.cancelSync` 先置空 syncJob 再异步写通知；ACTION_CANCEL 重投递幂等；引擎终态写为 conflated StateFlow last-writer-wins。
6. **进度条 scrub 状态机**：START/MOVE/FINISH/CANCEL 四相在 `ProgressScrubUiState` 内闭环，MOVE 只更新窄状态不触发全屏重组；Aurora* 测试锁定拖动数学（segment/fine-factor/stabilize）。
7. **AND-001 保存 scope**（progressSaveScope 独立于 viewModelScope）本身行为正确（回收站滑动杀进程后保存仍完成）—— 其缺陷仅是并发语义（BUG-002），不是 scope 设计。
8. **Aurora 无障碍 commitBy(-10s/+10s)**：START+FINISH 成对调用且 seekTo 与状态提交同帧，无半开 scrub 会话残留。
9. **零字节密文格式**：header-only 无尾块 + 严格 reserved 字节校验关闭了 chunk-less 文件的未认证字节洞（`headerRejectsNonZeroReservedOnEmptyFile`）。
10. **`SafVolume.usableSpace()` 返回 -1**：两个消费方（预检、逐文件复检）都把负值当"未知"放行，不会误判空间不足。

## Rejected Hypotheses

1. **SettingsViewModel DataStore 写路径 crash**（setVolumeBalance 等）——全部有 try/catch 且 CE 先传播。已由源码核查排除（与 BUG-004/005 的 StorageManagementVM 形成对比）。
2. **PlaybackRepository 95% 完成阈值溢出**——`duration * 0.95` 走 Double 运算，任何现实时长无溢出。
3. **SearchViewModel debounce/flatMapLatest 组合错配**——debounced query 与未 debounce 的搜索流会在最终发射时对齐；仅存在一帧的瞬时错配（文件夹匹配用旧词、文件结果用新词），自愈且不影响持久状态。降级为 cosmetic。
4. **dryRunDelete 绕过 storageOperationMutex 造成数据竞争**——确认绕过互斥，但其唯一写副作用是 progress 流（SCANNING 态短暂交叉显示），不改任何数据；数据变更入口（executeSync/executeDelete/reset）全部持锁。降级为 invalid-state(minor) 记录，不列为 bug。
5. **静音音频 → RMS=-Inf → +Inf 增益**——`coerceIn(-6, 6)` 钳制后放大静音仍为静音，无害。
6. **VideoQueue.consumeIds 竞争**——`AtomicReference.getAndSet` 原子读清，历史修复（6081303 时代）已闭环。

## Inconclusive Investigations

1. **DAO LIKE 元字符/大小写越界（`getByPathPrefix` 匹配 `dir_one`→`dirXone`、`Movies`→`movies`，可致 deleteFolder 误删兄弟目录密文）**——SQLite LIKE 语义确定（ASCII 大小写不敏感、`_`/`%` 为通配、无 ESCAPE），代码路径阅读成立，但决定性实验需要 Room androidTest（本环境无模拟器）。**高价值待办**：`LIKE ... ESCAPE '\'` + 绑定侧转义。
2. **SAF null cursor → NOT_FOUND → 元数据重建删活行**——Android 文档确认 provider 可返回 null cursor；`SafVolume.findChildDocId` 把 null 当"不存在"。需要 ContentResolver seam/androidTest 才能决定性验证。
3. **SyncService onStartCommand 触发丢失窗口**（上一 job 仍 active 但 consume 循环已退出）——机制阅读成立（亚毫秒窗口），但 Service 单测需 Robolectric/Instrumentation；影响低（下任一触发即恢复）。
4. **SAF rename-over-existing 使远端文件更新永久 FINALIZE_FAILED**——AOSP FileSystemProvider 行为假设成立即 bug；无 SAF provider 的 JVM 可测路径。
5. **RangeDecryptor size==0 跳过全部密文校验 / sink.write off+len 溢出 / KEK 短 blob 诊断性差**——行为确定（阅读+现有测试形态推演），严重性低，未单独实验（时间预算分配给高严重度候选）。
